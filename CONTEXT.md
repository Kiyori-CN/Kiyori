# Kiyori shared context

This file defines the stable product language and compatibility boundaries for this repository.
Current work status and implementation notes belong in `docs/TODO/`.

## Product identity

- **Kiyori** is the brand.
- **Kiyori** is the Android application and user-visible product name.
- **Kiyori** is the repository and Gradle root-project name.
- The project repository is `https://github.com/Kiyori-CN/Kiyori`.
- The Android application ID is `com.kiyori`.
- Android system surfaces, the default assistant persona, Kiyori-owned file-provider titles, WebChat, generated workspace display text, and Kiyori-owned companion UI use the Kiyori brand.

## Product position and ownership

- **Kiyori** is an all-purpose browser powered by Operit AI. Web access and content handling are the product center; video, music, reading, downloads, files, ad blocking, and later content capabilities are browser-owned domains.
- **Operit AI** is Kiyori's embedded AI subsystem. It owns AI conversation and AI-specific runtime capabilities, but it does not own the Kiyori application shell, global navigation, product identity, or system-wide settings.
- Every Kiyori capability may provide a human-facing page and an AI-facing capability contract. AI integrations call those contracts instead of directly driving Activities, Composables, or ViewModels.
- Kiyori has never had a user-facing release. The inherited Operit navigation drawer is not a published Kiyori interface, so the product-shell migration removes that design instead of maintaining a parallel legacy route.

## UI design sources

- **Kiyori Professional Browser Theme** owns the fixed application theme, the shared semantic-color vocabulary, and the browser protection domain. Material Blue 600 `#1E88E5` remains the primary action color, while `KiyoriSemanticTone` provides stable blue, green, purple, orange, red, cyan, and pink icon/container pairs for App Shell, settings, AI support pages, statuses, and browser content tools. The dedicated warm selection yellow is `#C48A00` in light mode and `#FFD166` in dark mode; it is reserved for the filled selected state of the five closed App Shell navigation icons and the clear-weather sun, and does not participate in stable entry-ID tone hashing. Large surfaces and text remain neutral. Browser Home, browser chrome, Full-Screen Web Search, and browser child-page surfaces stay neutral, while drawer tools may use small semantic icon badges without tinting the chrome or webpage. Software Home retains its fixed five-color search-frame border and fixed blue Search/AI selection. The theme does not use wallpaper dynamic color as a product default.
- **Operit Original UI** remains the visual-language authority for typography scale, shapes, component treatment, general icon behavior, dialogs, settings rows, glass effects, motion, and interaction density so AI and non-AI surfaces form one product. Browser Home, Minus-One Page, Settings Home, and their child pages must be compared against the current Operit source before UI implementation because these Kiyori surfaces directly reproduce Operit layouts and interactions. Kiyori-owned App Shell and browser chrome instead use the Legacy Kiyori outline Vector family. The inherited Operit purple palette and unconditional wallpaper dynamic color are intentional Kiyori product differences.
- **Legacy Kiyori Design Reference** is `Kiyori-CN/kiyori-android@24a2dfa91f0a4166dc58e5c4732d11861173f766`. It provides the page composition, navigation intent, browser behavior, and feature layout for Kiyori-owned surfaces.
- When the two sources differ, an accepted Kiyori product contract determines behavior, Operit Original UI determines visual treatment, and Legacy Kiyori Design Reference determines the Kiyori page's content structure.
- Source references are design and migration evidence, not runtime dependencies. New hard-coded visual systems must not be introduced beside the shared Kiyori theme.

## Product shell language

| Term | Definition |
| --- | --- |
| **Kiyori App Shell** | The Kiyori-owned root navigation, adaptive layout, window-inset, Back, and top-level state boundary. Operit AI is hosted inside this shell. Its five-item bottom navigation keeps the original outline vectors while unselected; the selected icon has no blue outline or selection container, and is rendered as a theme-aware warm-yellow fill with the original line details redrawn in the current page background color. |
| **Software Home** | The default center page shown after launch and the first of five primary destinations. It owns the three-page horizontal home space and uses one centered title-over-search column at the `<600dp`, `600-839dp`, and `>=840dp` width gates. On regular-height windows, the Search Frame top border is exactly `38.2%` of the available home height; short windows use the minimum top position that keeps the measured title visible. Compact, Medium, and Expanded cap content width at `544dp`, `584dp`, and `624dp`, with minimum horizontal padding of `24dp`, `48dp`, and `72dp`. |
| **Minus-One Page** | The page immediately left of Software Home. It is part of the home pager, hides the five-item bottom navigation, and reproduces the fixed legacy layout with four data cards and eight inert quick tools. Bookmark and Download observe their respective Browser Runtime counts and open the same shared drawers as Browser Menu; Collection and History remain zero-count placeholders. |
| **AI Home** | The full-screen Operit AI conversation page immediately right of Software Home. It hides the five-item bottom navigation, shares Software Home's pager state and fling physics, and has no edge-drawer gesture. Its top-right Browser, Terminal, and Workspace actions use stable blue, cyan, and purple icon colors; the two toggle actions add only their low-saturation semantic container while active. |
| **Browser Runtime** | The single in-process WebSession state owner shared by Browser Home, the 1×1 background anchor, the minimized indicator, and Operit AI browser tools. The anchor and indicator own no tabs, navigation, downloads, or userscript state. |
| **WebSession Profile** | The immutable website-data boundary of a WebSession: `normal` uses the default WebView profile, while each live `incognito` window group shares one uniquely named Kiyori AndroidX WebKit Profile generation. Closing the last window retires that generation immediately; the next group uses a new generation, and the next cold start deletes all retired Kiyori Profiles before loading any of them. |
| **Browser Home** | The immersive Kiyori browser root. It hides the five-item Kiyori bottom navigation and presents the shared Browser Runtime through browser-owned top-bar search, full-screen search, normal/incognito window overview, fixed browser-menu drawer, draggable child drawers, and bottom-bar chrome. |
| **Browser Presentation Owner** | The exclusive host currently mounting the active browser WebView: either `APP_SHELL` or `BACKGROUND_ANCHOR`. `APP_SHELL` is the only complete visible browser UI; `BACKGROUND_ANCHOR` is a 1×1 invisible, non-touchable, non-focusable attach point used only when Browser Home is not mounted. Browser Home owns a one-shot App presentation lease, so an explicit exit followed by Compose disposal cannot release twice. Repeated requests for the current owner are no-ops. A real `APP_SHELL <-> BACKGROUND_ANCHOR` change removes the old WebView and background window, verifies a null parent, crosses one `Choreographer` frame, and only then attaches the same View to the requested host without navigation or reload. |
| **Player Runtime** | The main process owns one `PlayerSession`, while the non-exported `:player` process owns the single MPV core. Together they own one immutable media request at a time, in-memory request headers, content file descriptor, playback/track/render state, and one explicit Surface lease state machine. A lease records the floating/fullscreen role, owner-instance token, monotonic generation, current and pending owner, native attach/detach state, transfer target, and one-shot fullscreen Activity launch/finish requests; Android `Surface` objects remain session-private. Fullscreen and browser-floating presentations transfer only the Surface and never reload media. The old owner must report `surfaceDestroyed`, then `PlayerSession` completes the single native detach before a pending target may attach. Both presentations use `PlayerSurfaceView`; browser floating is fixed full width, fixed `16:9`, zero side margins and square corners, initially attached to the browser bottom bar and movable only on the Y axis until its top edge reaches the browser top bar. Browser floating marks its Surface as a media overlay while the existing unique WebView retains its normal layer type. A new request creates and initializes the single mpv core before Android Surface callbacks. The first valid Surface is attached only after `mpv_initialize`; `loadfile` remains pending until that Surface lease completes native attach. This ordering matches the packaged mpvlibAndroid binding and the legacy Kiyori player. Decoder selection is the persisted mpv profile `fast/default/high-quality/gpu-hq/low-latency/sw-fast`; the unpublished default is `fast`. GPU Next selects `vo=gpu-next`, Vulkan selects `gpu-context=androidvk`, and both renderer switches apply when the unique mpv core is next created. Anime4K and playback speed begin from their stored value only when their independent memory switches are enabled. Volume enhancement raises mpv software volume to `150%` under a `300%` ceiling. The fullscreen control layer is the source-faithful `kiyori-android@24a2dfa9` layout and original drawable set. Its top status columns always expose value and unit/time as two single lines with identical `10sp` size, `11sp` line height and bold weight; the subtitle, danmaku, audio and aspect buttons keep their outer positions while rendering `24dp` icons. Its bounded `PlayerDebugLogBuffer` merges main-process lifecycle with `:player` command, MPV verbose, file-event and error records through the existing ordered AIDL callback. Each entry receives severity, stable sequence ID and one or more write-time diagnostic topics. The viewer polls the buffer revision at a bounded cadence, renders structured entries newest-first in a lazy list, and exposes one non-wrapping horizontal strip for all, error, warning-and-error, network/loading, playback, Surface/render, track/subtitle and runtime/MPV views. Header close and footer clear/copy/export stay outside the weighted log viewport; clear requires a second tap. Copy and export build a chronological full diagnostic report from the current view. Reports omit request-header values, Cookie, Authorization, URL query values, titles and private paths, and exports are written to `Download/Kiyori/exports`. Its arm64 native stack contains non-overlapping mpv and FFmpegKit AARs plus the single `libc++_shared.so` produced with the same Clang toolchain as `libmpv.so`; build and APK gates verify the required C++ symbols before delivery. |
| **Player Native Network Stack** | The main process keeps FFmpegKit's normal `libav*.so` names for FFmpeg tools and download remuxing. The non-exported `:player` process resolves `libmpv.so` and `libplayer.so` only against the fixed mpv input's FFmpeg `n8.1.2` closure, whose seven ELF files use equal-length `libmp*.so` SONAME/`DT_NEEDED` names and whose `libmpformat.so` was compiled with Mbed TLS 3.6.6. Player initialization copies the fixed `cacert.pem`, sets `tls-ca-file`, keeps `tls-verify=yes`, and disables the unshipped ytdl hook. Build and APK gates reject old FFmpeg dependency names in the mpv closure, missing TLS build markers, missing namespaced libraries, duplicate player native entries, or a mismatched C++ runtime. |
| **Browser Media Candidate** | Session-scoped evidence captured passively from the existing WebSession request path or a read-only DOM bridge. It preserves the browser-provided URL and actual request identity fields; MIME and URL shape are confidence evidence, never permission to rewrite or resolve another URL. |
| **Modal AI Drawer** | The Kiyori-owned, button-triggered left overlay that exposes AI top-level navigation without moving or rebuilding the page below it. Its scrim covers the window while its panel begins below the status bar. It has no edge or drag gesture. The Package, Permission, and Workflow quick cards reserve a dedicated top lane for count/status badges so text such as “正常” never covers the centered semantic icon. |
| **AI Top-Level Page** | AI Home, Packages, Permission Grant, Workflow, Assistant Configuration, Memory, Toolbox, a ToolPkg drawer destination, or AI Assistant Settings when entered from the Modal AI Drawer. Native roots retain independent state and child stacks; ToolPkg roots retain them only when their route declares `keepAlive=true`. |
| **AI Assistant Settings** | The one AI-owned settings root, shown to users as `AI 助手`. It contains model/API, functional-model routing, user preference, prompts, persona, response style, context, AI tool authorization, usage statistics, and external HTTP chat entries. The Modal AI Drawer and Settings Home enter the same page and persisted state. Drawer entry returns to AI Home; Settings Home entry uses `RouteEntrySource.KIYORI_SETTINGS` and returns to Settings Home. Crossing source families opens this root. |
| **AI Navigation Root** | An AI top-level route explicitly identified by its registered navigation-entry ID. Root ownership is stored on the route entry itself and is never inferred from route arguments, stack depth, or an instance-ID naming convention. |
| **Kiyori Edge-to-Edge Shell** | The window contract in which Kiyori-owned page backgrounds and the Modal AI Drawer scrim paint behind a transparent status bar. Interactive page content applies system insets, while the drawer panel itself starts below the status bar. |
| **Fixed Kiyori Theme** | The Kiyori-owned application visual contract. Light mode uses `#FFFFFF` backgrounds, `#202124` primary content, primary `#1E88E5`, and secondary `#536D79`; dark mode uses near-black backgrounds, layered gray surfaces, primary `#90CAF9`, and secondary `#B9CBD4`. Users can select light, dark, or system mode but cannot override the whole application palette. `KiyoriSemanticTone` supplies theme-aware blue, green, purple, orange, red, cyan, and pink icon/container pairs without becoming another persisted theme. AI chat background, bubbles, avatars, header, input, and local fonts remain AI-local personalization. Browser-owned surfaces use a fixed neutral ColorScheme and allow only small semantic accents for content tools and statuses. |
| **Permission Center** | A Kiyori system-level read-only overview and navigation destination that separates device capabilities from AI tool authorization. Its overview contains no direct permission switches and does not own another copy of either domain's persisted state. |
| **Device Capability Authorization** | Android and privileged-execution capabilities granted to Kiyori itself, including runtime permissions, file access, overlay, accessibility, battery exemption, Shizuku, Root, and debug capability. It is distinct from permission to invoke an AI tool. |
| **AI Tool Authorization** | The Operit AI policy that decides whether a registered tool is allowed, requires confirmation, or is forbidden. `ToolPermissionSystem` remains its single persisted source of truth. |
| **Software Home Search Frame** | The central same-background input surface, `114dp` high on regular windows and `96dp` in the short layout, with a fixed five-color `1dp` outline and no outer glow. Search/AI occupy one `120×32dp` rounded segmented control with equal halves, a center divider, clipped rounded press feedback, and fixed light/dark blue selection. The segments select the meaning and placeholder without navigating: Search opens Full-Screen Web Search when the frame is pressed, while AI enters the existing AI Home, preserves its conversation and draft, and requests focus for the real chat input after pager settlement. The saved mode survives return and configuration recreation; a cold launch starts in Search. The title ring is `18dp`. Attachment, voice, and camera remain immediate AI Home shortcuts. |
| **Software Home Weather** | The top-left location-derived city, current temperature, and WMO weather icon. Android location and `Geocoder` determine the city; Open-Meteo receives latitude/longitude for the current Celsius temperature and weather code. The icon uses warm yellow for clear weather, blue for partial cloud/rain, cyan for overcast/fog/snow, purple for thunderstorms, red for missing location permission, and orange for unavailable data. No unverified city or weather value is displayed or persisted. |
| **AI Home Quick Action** | A request-ID-bearing one-shot command from Software Home. It becomes consumable only after the shared pager settles on AI Home, then delegates input focus and IME display, attachment, microphone/fullscreen voice, or camera capture to the existing AI input owner and is consumed exactly once. |
| **Full-Screen Web Search** | The shared web-only search surface opened from the Software Home Search Frame or Browser Home top bar. It shares the browser search-engine owner and normal-mode recent records, requires a real normal/incognito Profile control, and represents normal with an open eye and incognito with a closed eye. The control is a borderless standard icon action; mode changes show only a short inverse-surface bottom message. Search-history tag deletion is staged until the user presses Done; Clear opens a bottom confirmation dialog and, once confirmed, clears the shared history immediately without a second Done action. Software Home always creates a new shared WebSession; Browser Home reuses the active tab only when its immutable Profile matches the selected Profile and otherwise creates a matching tab. It does not search bookmarks, browser history, files, mini apps, or AI conversations; those domains own their search pages. |
| **Settings Home** | The Kiyori-owned settings root preserves the fixed Legacy Kiyori `4/4/4/4` information structure while using adaptive light/dark settings tokens and semantic blue, green, purple, orange, red, cyan, and pink icon containers. The first card is ordered `账号与连接 / AI 助手 / 语音服务 / 小程序管理`; the first three open their real roots, while `小程序管理` remains an inert reservation for the bottom-navigation Mini App domain and must not route to AI packages, ToolPkg, scripts, or markets. Browser, player, downloader, appearance, and data entries also open their existing owners; rows without an implemented owner and all four header actions remain inert. |
| **Settings Detail Surface** | The shared visual shell for Kiyori-owned settings children. Account and Connections, AI Assistant Settings, Speech Services, Appearance, Data, Browser, Download, and Player settings use the same section title/description, borderless `16dp` white group card, two-line setting row, `0.6dp` divider, Material Switch, `42%` dependency-disabled state, and `26dp`-corner selection sheet with current-value and option-description rows. The root title is one continuously transformed text element: the first `72dp` of list scrolling moves it from the expanded `32dp / 60dp / 26sp` frame to the pinned `56dp / 16dp / 20sp` frame while the header content height contracts from `128dp` to `56dp`; the navigation action and real status-bar inset remain fixed. |
| **File Management Home** | The Kiyori-owned file root reproduced from the fixed Legacy Kiyori reference. It renders eight categories, seven quick-access entries, and four storage locations with zero placeholder counts. The phone-storage row reads available and total bytes from the app's actual data volume on composition and host resume; every page action remains inert. |
| **Browser Settings** | The Kiyori browser-settings page opened from Settings Home or the fourth browser-menu row. Its five semantic groups have `3/5/4/6/6` entries: Plugin and Session, Home/Tab/Gesture, Media Sniffing, Site Permission/Data, and Display/Advanced. `WebSessionBrowserSettingsStore` is the one owner for the custom home URL, search-bar media-candidate entry, automatic floating playback, webpage external-app policy, and webpage geolocation policy; `CookiePrivacyManager` owns the explicit ordinary-site Cookie clear action. The two media switches exist only in the Media Sniffing group; the `MEDIA_CANDIDATES` drawer contains format filters and candidate actions but no settings. Rows without a current page-owned runtime consumer are visibly disabled and never open an empty page. |
| **Download Settings** | The Kiyori download-settings page is a projection of the single version-2 `BrowserDownloadSettingsStore`. Its five groups and entry counts are `5/4/2/2/1`: Downloader and Performance, Network and Background, M3U8 and Storage, Installation and Confirmation, and Network Protocol. Default destination is one selection across the application directory, public ordinary-file transfer, and a persisted SAF tree; public transfer and SAF remain mutually exclusive and `BrowserDownloadManager` owns permission release. Network policy selects any network or Android-classified unmetered network, roaming is an independent opt-in, result notifications can be disabled, and the system notification-settings entry opens the app channel settings. When Android System DownloadManager is selected, only internal-engine-owned rows are dependency-disabled; engine choice, network policy, roaming, system notification settings, and skip-confirmation remain available. |
| **Browser Download Runtime** | `BrowserDownloadManager` remains the only persisted Kiyori task, queue, scheduler, and file-owner. Its `AtomicFile` JSON records publish one `StateFlow` projection shared by Browser Home, Shell, Minus-One, the Download Drawer, notifications, and AI events; no WorkManager database or second download owner exists. File names are reserved before queue insertion, confirmation requests use a bounded FIFO, persistence is serialized and atomic, and interrupted HTTP work is restored to an explicit non-networking state until the user resumes it. Android 14 and newer run network work through one persisted user-initiated data-transfer `JobService`; Android 8 through 13 use one `dataSync` foreground service. The runtime notification reports aggregate progress and speed, supports Pause All, and opens the shared Download Drawer; terminal notifications report completion or failure. Each new task freezes concurrency, ordinary Range threads, M3U8 threads, offline-package policy, public-transfer policy, chunk size, HTTP protocol, network policy, roaming policy, and optional SAF target. Runtime scheduling and Android `DownloadManager` both enforce the selected network and roaming rules. Ordinary HTTP uses one task-owned `BrowserDownloadTransport` with bounded retry classification, strong ETag or Last-Modified `If-Range` validation, exact `206`/`Content-Range` checks, rollback of failed attempts, and `max(chunkSize, 1 MiB)` range parts. M3U8 text is size-bounded and must begin with `#EXTM3U`; package mode follows at most four highest-bandwidth master levels, rejects cycles and external audio/video/subtitle rendition playlists rather than producing an incomplete package, deduplicates repeated and byte-range resource URLs, downloads `KEY`, `MAP`, `PART`, and media resources in bounded batches, removes live-only preload hints, verifies every local resource before commit, and keeps the playlist plus companion directory together for rename and delete. Completed ordinary files can rename, change suffix, move to SAF, copy their original URL or saved location, share, transfer publicly, and redownload. Status output removes URL credentials, query, and fragment; explicit Copy URL retains the original address. APK auto-clean no longer uses a timer: the task record persists the expected package name and version, a SAF APK uses a short-lived cache copy only to read package metadata while the installer receives the original granted SAF URI, and the original task/file is removed only after Android broadcasts an exact installed package/version result; disabling the setting clears pending install state. A confirmed `SYSTEM` request is owned only by Android `DownloadManager` and is never mirrored into Kiyori JSON or progress. The Download Drawer adds case-insensitive search, status filters, visible eligible Select All, separate batch cancel/delete semantics, accessible controls, and explicit record-only versus record-and-file deletion. |
| **Browser Network Log** | The current WebSession's in-memory request record captured by its existing Android WebView `shouldInterceptRequest` path. Each session keeps at most 500 entries and clears its own log on navigation or explicit user clear. Search and `all / video / audio / image / web / other` filters are presentation state. A cross-host marker is a factual host comparison, not an ad or failure verdict. Copy, download, external-open, and details actions use the recorded URL and existing browser/download owners. The log does not invent response status, response MIME, response bodies, blocking state, or playback capability, and its UI never reloads a resource for preview. |
| **Kiyori Capability API** | UI-independent contracts through which Operit AI observes and operates Kiyori browser, media, reader, file, download, and later domains. |
| **High-Impact AI Action** | An AI-requested operation with destructive, privacy, financial, external-communication, account, permission, or persistent-state impact. It requires explicit authorization and an inspectable operation record. |

## Navigation contract

- App launch opens the center Software Home page.
- The Software Home horizontal order is Minus-One Page, Software Home, then AI Home.
- All three home pages use one `PagerState` and one fling behavior. Movement follows the pointer, and a new reverse drag can cancel an unfinished fling; Shell state changes only after the pager settles.
- The five primary destinations are Software Home, Browser Home, Mini App Home, File Management Home, and Settings Home.
- The five-item bottom navigation is visible on Software Home, Mini App Home, File Management Home, and Settings Home. Browser Home is an immersive root with its own bottom bar; Minus-One Page, AI Home, Full-Screen Web Search, child pages, and immersive content pages also hide the Kiyori bottom navigation.
- The current browser presentation contract is `APP_SHELL <-> BACKGROUND_ANCHOR`. Only Browser Home mounts complete browser chrome, drawers, text-selection actions, and the browser floating player. Leaving Browser Home transfers the same active WebView to the fixed 1×1 background anchor when overlay permission already exists and shows the minimized indicator. Tapping that indicator opens the existing `MainActivity` Browser Home. Long-pressing it consumes the open action and creates one transparent `28dp` temporary WindowManager close action outside the indicator's upper-right edge, rendering a smaller `16dp` red close icon. That close window is non-touchable while the original gesture remains pressed, becomes touchable after release, follows indicator dragging, stays inside the physical display bounds, and is removed after three seconds. Activating it routes through the same `onExitBrowser` presentation teardown used by the fourth browser-menu row. The temporary close window owns no WebView, session, navigation, download, or Browser Runtime state. Browser Home activity keeps no empty background-anchor window, direct Browser Home entry does not pre-mount the anchor, and cross-ViewRoot transfer uses a detach/frame/attach transaction. Historical expanded-overlay, overlay Back, cutout, IME, and focusable-window clauses retained in older long-form records are superseded and are not current behavior.
- Browser Home is the only complete presentation of one Browser Runtime. Tabs, the active WebView, history, bookmarks, downloads, userscripts, and pending confirmations are never copied into the 1×1 background anchor or minimized indicator. Browser downloads retain one atomic JSON record set as their only persisted Kiyori task state, publish one snapshot `StateFlow`, and use one global FIFO scheduler. Each HTTP task freezes ordinary Range concurrency, M3U8 concurrency, offline-package/public-transfer policy, chunk size, protocol, target directory, network policy, and roaming policy when created; later settings changes do not alter its running plan. Internal dispatch enters `BrowserDownloadManager`; system dispatch gives Android `DownloadManager` complete ownership and never mirrors progress into Kiyori. Website data remains isolated by immutable WebSession Profile, normal sessions alone write shared search/browsing history, and Browser Home entered from AI Home returns to AI Home after releasing the App Shell presentation.
- Operit AI discovers human-created browser state through `browser_tabs list`. The list enumerates the same Browser Runtime used by Browser Home and the background anchor, exposes each stable `session_id`, `profile`, title, URL, index, and active state, and requires the intended tab to be selected before `browser_snapshot`, click, type, or navigation operations. `browser_tabs create` accepts `profile=normal|incognito`; omission uses the Browser Runtime default Profile. Incognito isolates website data, not Kiyori AI actions already authorized by the user.
- Browser Home's top bar is ordered Back, Search, and Refresh. Refresh always reloads the active WebView, retains the refresh glyph during loading, and uses the same circular press surface as the full-screen search Profile action. The top-left action exits Browser Home according to its recorded Shell source; webpage history is owned by the bottom-bar Back and AI `browser_navigate_back`. Search opens the shared full-screen web search surface without recreating the active WebView. Its Profile control is always present; submission reuses the active tab only when the selected immutable Profile matches, and creates a matching shared WebSession otherwise. Engine selection and recent records remain browser-owned state. The full-screen search top row reuses Browser Home's exact `8dp / 6dp / 40dp / 42dp` outer-gap-action-input geometry, so Back, the fixed-width input, and Profile occupy the same absolute slots. The input wraps instead of scrolling horizontally, grows downward from one through three visible lines with a top-anchored content-size animation, and then keeps its three-line viewport while the text scrolls vertically. The full-screen search surface shows the selected engine icon instead of its name, opens a blue-tinted engine panel over the lower content, presents the active page title and URL with copy/edit actions, and renders search records as adaptive tags whose staged deletions commit only from the explicit Done action. The bottom bar is ordered Back, Forward, Home, Tabs, and Browser Menu. Home navigates the active WebSession to the custom home URL, and human/AI new-tab creation uses the same URL. App Shell and browser bottom bars use five equal slots with `16dp` horizontal, `0dp` top, and `6dp` bottom padding, `44dp` circular targets, and `26dp` icons; the App Shell center icon is `25dp`. The browser window counter is a `20dp` square with a `1.75dp` outline. Browser Menu opens a content-sized four-row surface: its three five-column rows use `21dp` outline icons in `32dp` containers with `1dp` row spacing, while its fourth row directly distributes three `46×36dp` actions with `22dp` icons and no synthetic five-slot placeholders. History, bookmarks, downloads, userscripts, network logs, page source, and capability explanation pages open draggable child drawers. User-Agent is a direct modal action: opening it closes the menu and shows `Android / PC desktop / iPhone / Symbian Wap / custom global / custom website`. `WebSessionBrowserSettingsStore` owns the global mode, custom global value, and normalized-domain site rules. An explicit session UA has highest priority, then a matching site rule, then the global mode; applying any choice updates the same WebSession WebViews and reloads only the active page. The menu's Incognito action opens the real window overview, AI Dialogue returns to AI Home, and Exit Browser uses a power icon and removes the presentation layer while retaining sessions. The fourth-row Browser Settings button opens the same Shell child as Settings Home; App Shell presentation keeps the existing WebView mounted underneath, while overlay presentation first minimizes its focusable window and uses the explicit internal Kiyori Intent. The window overview has only normal/incognito selectors at the top, uses 2/3/4 columns, filters the one WebSession registry by immutable Profile, and displays `5:8` vertical in-memory thumbnails that fit the complete current WebView viewport without cropping. New and clear actions affect only the selected Profile. Unsupported Multi-Profile or failed cold-start private-profile cleanup disables incognito explicitly and never substitutes a normal window.
- Full-screen search uses Browser Menu scale rather than page-title scale: its action icons are approximately `21dp`, labels are `11–12sp`, and engine cards, current-page actions, history tags, and vertical gaps are compact. Copy/Edit glyphs sit optically closer to their labels. The `26dp` history trash glyph stays inside a fixed `34dp` header row, so switching to Clear/Done does not move the title vertically. The engine-panel scrim dismisses the panel when the surrounding area is tapped. Tapping the current-page title/URL surface dismisses search and returns to the already active WebView without a reload.
- Browser Home records the last submitted text query only in presentation state. A text search exposes the horizontally scrollable nine-engine quick-switch bar below the top row; selecting another engine persists that engine and resolves the same query in the active Profile, while address navigation and the explicit close action hide the bar. The Browser Menu fourth row uses `2:1:2` weighted slots so Exit and Settings align midway between the first/second and fourth/fifth columns above, with Collapse remaining centered.
- `WebSessionBrowserSettingsStore.allowWebPageOpenApp` is the only external-app authorization owner. Kiyori has no per-navigation external-open prompt state or UI. An external scheme launches only for a main-frame request with an explicit user gesture while the saved setting is enabled; automatic redirects and disabled-policy requests are consumed without opening another application.
- Browser Network Log exits Browser Menu into the existing draggable child-drawer host. It projects only the active session's bounded request list, keeps search/filter/action-dialog state in the presentation, and clears only that session's network entries. A logged HTTP or HTTPS URL can be copied, handed to the current default Browser Download Runtime with the active Profile request identity, opened externally by explicit user action, or inspected without navigating/reloading the WebView. Response status, blocking and playback remain absent until their own runtime owners provide confirmed data and commands.

## AI action authorization

- Risk is assigned to a concrete command and its target, scope, reversibility, data sensitivity, and external impact. A tool name alone never determines risk.
- **R0 Read-Only** operations do not change local or external state and need no operation confirmation after the tool gate permits them.
- **R1 Low-Impact** operations are local, bounded, and easy to reverse or stop. Persistent tool authorization may permit them without per-operation confirmation.
- **R2 High-Impact** operations change persistent state, access sensitive data, affect multiple objects, or prepare external impact. They require one-time confirmation by default; an explicit session grant is allowed only for a fixed target and scope.
- **R3 Critical** operations are difficult to reverse, privileged, financial, account-sensitive, or create an external action that cannot be recalled. Every operation requires confirmation; session and persistent bypass are prohibited.
- `FORBID`, `ASK`, and `ALLOW` control whether a tool may be invoked. The R0-R3 contract separately controls whether the concrete operation may produce side effects. `ALLOW` cannot bypass R2 or R3 confirmation.
- When `ASK` and an R2 or R3 confirmation apply to the same command, Kiyori presents one combined authorization decision rather than consecutive prompts.
