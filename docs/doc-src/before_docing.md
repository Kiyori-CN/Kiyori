# 文档维护规范

项目文档必须帮助读者快速找到权威事实、执行正确命令并理解验证边界。文档不是过程日志的堆放区，也不能把计划、推断或历史结果写成当前已经成立的事实。

## 文档职责

- 根 `README.md` 面向用户与新贡献者，保持简洁、可操作并避免内部实现流水账。
- 根 `CONTEXT.md` 记录术语、模块所有权、状态、协议、兼容标识和不变量。
- `docs/doc-src/` 保存长期维护的架构、决策、开发、协议、研究和测试文档。
- `docs/TODO/` 保存正在推进或仍有验收边界的专项计划与证据。
- `AGENTS.md` 只记录工作方式和验证规则，不作为产品功能文档。

## 文件与目录命名

- 根入口使用约定名称：`README.md`、`README.en.md`、`CONTEXT.md`、`AGENTS.md`。
- 新增 TODO 目录使用小写 `snake_case`，入口为 `index.md`。
- 新增分步文档使用两位数字前缀和描述性小写名称，例如 `01_inventory.md`。
- 已建立且被广泛引用的稳定文件名可以保留；需要迁移时必须同步所有引用并通过链接检查。
- 文件名应表达主题，不使用 `new`、`final2`、`temp`、`misc` 等无法长期维护的名称。

## 内容要求

- 开头说明目标、适用范围、非目标、状态和权威边界。
- 明确区分已验证事实、设计决策、推断、未知项和待设备/远端/用户验收内容。
- 命令必须可复制，路径和参数必须与当前实现一致。
- 重要设计说明“为什么这样做、违反约束会怎样”，避免复述代码。
- 不复制大段源码、日志或终端输出；保留最小证据、文件位置、命令和结果摘要。
- 历史提交、APK 哈希、测试数量和版本必须标注观察日期，不能当作当前状态复用。

## 链接与资源

- Markdown 文档优先使用相对链接。
- 移动文件前使用 `rg` 检查所有路径、锚点和代码引用。
- 需要图片时才在 `docs/assets/` 下创建明确主题目录；只提交被正式文档实际引用的资源，不保留零引用截图、历史导出或临时报告。
- 不引用本机绝对路径作为普通读者必须具备的资源；开发机专用路径只能出现在明确的本地运维说明中。

## TODO 生命周期

1. 优先复用现有专项 TODO，不为同一目标创建平行状态源。
2. 新任务在 `index.md` 中记录目标、范围、验收、依赖、风险和阶段状态。
3. 每个阶段只在实现与相称验证完成后标记 `DONE`。
4. 设备、远端、Release 或用户现场验收未完成时保持 `verification_pending`。
5. 归档前更新所有引用；经项目约定确认后移入 `docs/.META/legacy/TODO/`。

## 提交前检查

至少确认：

- 文档职责没有与 `README.md`、`CONTEXT.md` 或其他正式文档重复。
- 所有相对链接有效，标题层级从一个一级标题开始且连续。
- 路径、命令、版本、分支、状态和产物说明与当前仓库一致。
- 未包含凭据、私人日志、Cookie、令牌、签名材料或不必要的本机信息。
- 运行 `ci/script/check_markdown_links.py` 对应的仓库检查。
