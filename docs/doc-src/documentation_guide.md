# 文档维护规范

项目文档必须帮助读者快速找到权威事实、执行正确命令并理解验证边界。文档不是过程日志的堆放区，也不能把计划、推断或历史结果写成当前已经成立的事实。

## 文档职责

- 根 `README.md` 面向用户与新贡献者，保持简洁、可操作并避免内部实现流水账。
- 根 `CONTEXT.md` 只记录高频术语、所有权和不变量，适合会话按需注入；领域细节放入 `doc-src/contracts/`。
- `docs/user-guide/` 保存用户首次使用、配置和排障说明，不放开发门禁与内部调用链。
- `docs/doc-src/` 保存长期维护的架构、决策、开发、协议、研究和测试文档。
- `docs/TODO/` 保存正在推进或仍有验收边界的专项计划与证据。
- `AGENTS.md` 只记录工作方式和验证规则，不作为产品功能文档。

### 根 README 变更门槛

根 `README.md` 是面向用户和新贡献者的稳定入口，维护时遵循以下顺序：

1. 先确认变更属于项目定位、用户可见能力、安装/配置/构建入口或文档导航；内部实现细节放到 `CONTEXT.md` 或 `doc-src/`。
2. 先更新真正的权威文档，再在 README 中用短段落或表格链接过去；README 不复制完整契约、排障日志和专项进度。
3. 保持既有目录顺序、标题锚点和中英文入口稳定。需要重命名或移动时，先用 `rg` 查找引用，再一次性更新引用和目录。
4. 完成后通读渲染结构：标题层级、空行、表格、代码围栏、链接、图片替代文本和移动端可读性都必须通过检查。

README 的每次修改都应能回答“谁需要这段信息、从哪里获得事实、读者下一步做什么”。无法回答的问题应移到更合适的文档层级。

#### 哪些变化需要改入口

| 本轮变化 | 应当更新 | README 处理 |
| --- | --- | --- |
| 内部修复、重构、单次测试或构建 | 正式契约与专项证据 | 通常不改 |
| 调整按钮、拖柄、排序、弹层或错误提示 | 相应用户指南；语义变化同步领域契约 | 只有能力概览或上手路径改变时才改 |
| 安装渠道、首次配置、支持范围或构建入口改变 | 用户指南或构建指南 | 更新必要说明，两种语言同时核对 |
| 产品定位、核心能力、重要限制变化 | 对应决策或契约 | 更新概览，不把计划当成已实现 |
| 有证据的纠错、翻译同步、明确要求的文档整理 | 发现问题的权威入口 | 可修正；记录来源并保留稳定锚点 |

README 不维护逐控件说明、内部类名清单、每轮 APK 哈希、测试数量、提交日志或验收队列。
这些内容即使真实，也应由相应指南、契约或专项持有。

#### 同一变更中的核对记录

在已有 `docs/TODO/<专项>/index.md` 或本轮分项新增以下记录。先写修改依据和预期验证，
完成后换成实际结果；不新建平行日志，不在 README 正文或隐藏注释中堆放审核记录。

```markdown
### README 变更说明

- 目标读者：具体用户或新贡献者，以及需要完成的操作。
- 变更理由：本轮触发原因、改变的入口及为何不能只修改详细指南。
- 权威来源：本轮核对的正式文档、源码符号、配置或发布说明。
- 排版验证：实际执行的结构检查、链接核对和宽屏/窄屏预览结果。
- 双语核对：中英文能力、限制、安装渠道与导航的核对结果；只改一版时说明原因。
```

`check_documentation.py --base <base-sha>` 检测两份根 README 相对基线的变化，只接受本次
TODO 差异中新增的五项非空说明。新建分项必须先暂存才能进入 Git 差异；可先写入已有专项。
CI 复用 PR 的 base SHA 执行此检查。检查器不判断说明是否真实、有说服力或符合用户授权，
维护者仍须审阅原始差异，不能用占位文字、旧记录复制或过晚选择基线绕开核对。

## 文件与目录命名

- 根入口使用约定名称：`README.md`、`README.en.md`、`CONTEXT.md`、`AGENTS.md`。
- 新增 TODO 目录使用小写 `snake_case`，入口为 `index.md`。
- 新增分步文档使用两位数字前缀和描述性小写名称，例如 `01_inventory.md`。
- 现行专项编号只表达原有阅读顺序，不重新编号填补历史缺号；编号后使用小写 `snake_case`，缩写同样小写。
- 已建立且被广泛引用的稳定文件名可以保留；需要迁移时必须同步所有引用并通过链接检查。
- 文件名应表达主题，不使用 `new`、`final2`、`temp`、`misc` 等无法长期维护的名称。

已有 `docs/TODO`、`doc-src`、`user-guide`、`dev-core` 等目录是稳定入口；不为统一大小写而
改动整棵目录。`BUILDING.md` 等生态入口、公开脚本指南、协议夹具、许可证和上游路径保持原有用途。
新目录必须有实际文档与入口，不预建 `.META`、空资源目录或泛称“其他”的资料堆放区。

迁移先列出旧路径 → 新路径，核对大小写碰撞、同名文件、相对链接、页内锚点、裸路径、脚本与
机器消费者，再更新目录。历史正文只修正可导航引用，原日期、提交、哈希和状态保留。
外部指向旧分支路径的书签无法由仓库搜索穷尽；完整目录用于重新定位，精确历史阅读使用提交固定链接。

## 内容要求

- 开发文档使用简体中文；类名、API、schema、枚举和命令保留源码拼写。`README.en.md`、明确双语入口、协议样例及上游许可证原文按各自用途保留语言。
- 使用 UTF-8 无 BOM、LF 换行；每篇一个一级标题，标题不跳级，标题和列表前后留空行。
- 表格使用一致的分隔行和左右空格；长段落按职责拆成小节或列表，避免把多条独立契约塞进单个表格单元。
- 每个表格行写在同一物理行，表头、分隔行与数据行列数一致；单元内管道即使在反引号中也写为 `\|`。段落里的多个步骤改成列表。
- 代码围栏标明语言；协议样例、命令、许可证与机器消费文本不因排版而改写语义。
- 开头说明目标、适用范围、非目标、状态和权威边界。
- 明确区分已验证事实、设计决策、推断、未知项和待设备/远端/用户验收内容。
- 命令必须可复制，路径和参数必须与当前实现一致。
- 重要设计说明“为什么这样做、违反约束会怎样”，避免复述代码。
- 不复制大段源码、日志或终端输出；保留最小证据、文件位置、命令和结果摘要。
- 历史提交、APK 哈希、测试数量和版本必须标注观察日期，不能当作当前状态复用。

### 长文与阅读节奏

- 超过约 400 行或有多个独立主题的文档优先提供页内目录，默认只列二级标题；不要把所有小标题塞进首屏。
- 使用清楚的中文标题、短段落和主题分组；列表适合并列规则，表格适合对照，代码围栏用于可复制输入和原样输出。
- 当前任务入口先给当前范围、阶段、未验收边界和下一步，再链接分项与历史；新进度放在最新阶段，避免不断向文件尾部追加导致入口过时。
- `<!-- doc-toc:start -->` 与 `<!-- doc-toc:end -->` 之间是派生的页内导航；标题变化后用 `--write-catalogs` 同步，正文不由生成器重写。
- 图表必须帮助解释事实；没有图片的文档不为装饰新增截图。Mermaid 图旁保留可理解的正文，不能依赖特定渲染器才读懂关键流程。

## 链接与资源

- Markdown 文档优先使用相对链接。
- 移动文件前使用 `rg` 检查所有路径、锚点和代码引用。
- 需要图片时才在 `docs/assets/` 下创建明确主题目录；只提交被正式文档实际引用的资源，不保留零引用截图、历史导出或临时报告。
- 不引用本机绝对路径作为普通读者必须具备的资源；开发机专用路径只能出现在明确的本地运维说明中。

## TODO 生命周期

1. 优先复用现有专项 TODO，不为同一目标创建平行状态源。
2. 新任务在 `index.md` 中记录目标、范围、验收、依赖、风险和阶段状态。
3. 每个阶段只在实现与相称验证完成后标记 `DONE`。
4. 设备、远端、Release 或用户现场验收未完成时保持 `verification_pending`。
5. 总索引只导航，逐项历史证据归入 `docs/TODO/history/YYYY-MM/` 并链接原专项；不得把未完成专项整体归档成已完成。

## 提交前检查

至少确认：

- 文档职责没有与 `README.md`、`CONTEXT.md` 或其他正式文档重复。
- 所有相对链接有效，标题层级从一个一级标题开始且连续。
- 路径、命令、版本、分支、状态和产物说明与当前仓库一致。
- 未包含凭据、私人日志、Cookie、令牌、签名材料或不必要的本机信息。
- 运行 `ci/script/check_markdown_links.py` 对应的仓库检查。
- 若修改根入口，额外核对 `README.md`、`CONTEXT.md`、`AGENTS.md` 和 `docs/README.md` 的职责没有互相复制；在提交说明中记录这项核对。

## 可复制检查入口

使用项目 `.venv`。下列为 Windows 示例，Linux/macOS 将解释器替换为 `.venv/bin/python`：

```powershell
.\.venv\Scripts\python.exe -B ci/script/check_documentation.py --repository .
```

新增、移动或重命名文档后，更新确定性目录并再次检查：

```powershell
.\.venv\Scripts\python.exe -B ci/script/check_documentation.py --repository . --write-catalogs
```

该命令更新 `docs/CATALOG.md`、`docs/TODO/catalog.md` 与已标记的页内导航，不重写正文。工作区检查包含未忽略的新文档；形成提交后，仍需用已确认的基线 SHA 与候选提交运行 `check_markdown_links.py --base <base-sha> --candidate HEAD`，防止工作区未跟踪文件掩盖候选树断链。

上述命令验证文件路径、常用本地锚点、编码与结构排版；实际渲染、复杂语法、外部站点与 API 行为仍需按变更范围复核。历史记录、协议夹具与第三方原文保留用途，不因文字清理扩大事实承诺。

README 改动使用任务起点 SHA；以下变量必须替换为本轮实际基线：

```powershell
$documentationBase = "<本轮起点的完整提交SHA>"
.\.venv\Scripts\python.exe -B ci/script/check_documentation.py --repository . --base $documentationBase
.\.venv\Scripts\python.exe -B -m unittest ci.test.test_documentation ci.test.test_markdown_links
```

### 检查范围与人工审阅

| 验证 | 自动覆盖 | 人工或独立证据 |
| --- | --- | --- |
| 结构与排版 | 跨平台路径大小写碰撞、专项命名、UTF-8、BOM、LF、末尾换行、标题层级、列表前空行、表格列数、顶层围栏语言与闭合 | 嵌套容器/复杂 HTML、长段落、语言质量、图片含义 |
| 导航 | 文件链接、GFM 常用标题锚点、显式 HTML ID、HTML 本地资源、派生目录 | 外部 URL、动态站点、复杂渲染语法、外部旧书签 |
| README 约束 | 两个语言入口相对 base 的变化与新增五项说明 | 修改必要性、来源正确、翻译准确、信息未重复 |
| 候选提交 | `check_markdown_links.py` 核对真实 Git 树与 gitlink | 工作区存在不等于已经跟踪或提交 |
| 事实与效果 | 检查器自身回归分支 | 源码/命令比对；宽屏与约 390 px 窄屏渲染，目录点击、表格和代码横向滚动 |

自动检查扫描父仓全部 Markdown；子模块文档按独立仓库维护。协议夹具、运行时模板和许可证
不按开发文档改写。复杂 Markdown 不能只靠正则或退出码判定最终视觉；预览时避免把私有正文上传到第三方渲染服务。
